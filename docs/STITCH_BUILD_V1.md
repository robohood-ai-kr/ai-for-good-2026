# RoboHood Stitch 앱 빌드 v1

> 아래는 Stitch ZIP을 처음 병합했을 때의 기록입니다. 현재 기본 빌드는 새 생성 이미지에 맞춘 v1 개선본이며, 소스·기능·검증 결과는 [현재 구현 안내](UI_REFINEMENT_V1.md)를 따릅니다. 아래 원격 자산·중복 툴바·모바일 검증 한계 설명은 초기 빌드에만 해당합니다. `scripts/build.mjs`는 원본 가져오기 이력으로 보존하며 기본 빌드는 `scripts/build-refined.mjs`입니다.

## 결과

네 개의 Stitch ZIP을 **제조업 21개 화면**과 **소상공인 20개 화면**으로 병합한 두 개의 정적 프런트엔드 앱입니다. 두 기획을 하나의 제품으로 합치지 않았으며 각각 v1입니다. 메뉴·역할·브라우저 저장소·빌드 폴더가 분리됩니다.

기존 기획서·PNG 갤러리는 보존했습니다. 이 결과가 각 MVP 명세의 서버·데이터 처리 수용 기준을 모두 충족했다는 의미는 아닙니다.

## 실행

Node.js 22 이상, npm을 사용합니다.

```sh
npm ci
npm run dev
```

- 앱 선택: `http://127.0.0.1:4173/`
- 제조업: `http://127.0.0.1:4173/manufacturing/`
- 소상공인: `http://127.0.0.1:4173/small-business/`
- 기존 빌드만 실행: `npm run preview`
- 포트가 사용 중이면: `npm run preview -- --port 4174`
- 종료: 서버를 실행한 터미널에서 `Ctrl+C`

```sh
npm run build                  # 두 앱 빌드
npm run build:manufacturing    # 제조업만 빌드
npm run build:small-business   # 소상공인만 빌드
npm test                       # 원본·화면·링크·상태·HTTP 검사
npm run package                # 두 앱 빌드·검사·ZIP 생성
```

개별 빌드는 다른 제품의 기존 폴더를 지우지 않습니다. 시작 페이지에는 이번에 선택한 제품만 표시합니다. 전체 `build` 또는 `package`를 실행하면 두 제품 선택 화면이 생성됩니다.

## 폴더와 수정 경계

| 경로 | 용도 |
|---|---|
| `design/stitch/v1/` | 제품별 원본 HTML·PNG·Stitch 디자인 문서·해시 기록 |
| `apps/shared/catalog.mjs` | 두 제품의 별도 화면 목록·메뉴·역할·대표 흐름 |
| `apps/shared/app.mjs` | 검토된 공통 UI 동작·입력 저장·모달·검색 |
| `apps/shared/state.mjs` | 조건 확인·수집·검수·이용 승인·FDE 모의 실행 상태 |
| `apps/shared/app.css` | 공통 셸·레이아웃 보정·초점·모바일 스타일 |
| `scripts/build.mjs` | 원본에서 실행 코드 제거, 화면 연결, 로컬 Tailwind CSS 생성 |
| `dist/manufacturing/` | 독립적으로 호스팅 가능한 제조업 빌드 |
| `dist/small-business/` | 독립적으로 호스팅 가능한 소상공인 빌드 |
| `dist/packages/` | 각 앱 ZIP 및 해시 manifest |

`dist/`는 생성물이며 Git에서 제외합니다. 원본 시안을 고쳐 덮어쓰기보다 빌드 변환 또는 새 앱 소스를 수정한 뒤 다시 빌드합니다. 장기 제품 개발에서 공통 컴포넌트로 이관할 수 있지만 이번 빌드는 React·MUI 채택이나 백엔드 구축을 전제하지 않습니다.

각 앱은 상대 경로를 사용하므로 해당 빌드 폴더만 정적 서버에 올릴 수 있습니다. ES 모듈과 브라우저 저장소를 사용하므로 HTML 더블 클릭(`file://`) 대신 HTTP 서버로 실행합니다. 외부 배포·도메인·Git 커밋·푸시는 이번 작업에 포함하지 않았습니다.

## 구현된 데모 동작

- 41개 화면의 개별 URL, 공통 메뉴, 상단 화면 선택, 역할별 시작 화면.
- 과제 요청 입력·필수 제목 및 양수 수량 확인, 화면 입력 임시 저장·재조회. 연락처·비밀번호 등 실제 개인정보를 입력하지 않습니다.
- 표 검색과 일부 상태 필터. 시안의 페이지 번호·서브 탭·미구현 동작은 안내만 제공하며 전체 서버 검색이 아닙니다.
- 5개 조건 미확인 시 수집 시작 차단, 모의 RGB 촬영·영상 구간 기록, 검수 대기 제출.
- 별도 검수 역할의 승인·사유 있는 보완, 별도의 평가 목적 이용 신청·운영팀 모의 승인.
- 이용 승인 전 데모 메타데이터 내보내기 거부. 승인 후 JSON 다운로드. 실제 원본 영상·이미지를 제공하지 않습니다.
- 제조업 FDE 역할에서만 장치 UI의 모의 실행 상태 변경. 실제 모델·물리 시뮬레이터 실행이 아닙니다.
- 검수 승인과 모의 지급 대기를 분리. 실제 지급·보험·협약·채용 없음.

각 화면의 상단 **진행 기록**은 브라우저에 저장한 상태를 보여줍니다. 그 아래 Stitch 원본의 표·지표·이미지·지도는 서로 다른 시점의 정적 예시입니다. 동적으로 갱신되는 서버 데이터로 해석하지 않습니다.

두 앱은 `robohood:manufacturing:v1`, `robohood:small-business:v1` 키를 각각 사용합니다. 다른 브라우저·PC와 동기화되지 않습니다. ‘화면·안내 → 이 앱의 데모 기록 초기화’는 선택한 앱의 기록만 초기화합니다.

## 대표 검증 경로

1. 제조업 `MF-03 → MF-05`에서 제목을 입력하고 등록하면 `MF-06`의 ‘연결된 내 데모’에 반영됩니다. `MF-05`로 돌아가면 저장한 입력을 재조회합니다.
2. `MF-14`에서 운영팀 역할의 모의 실행은 거부됩니다. 상단 역할을 FDE로 바꾸면 모의 실행 안내를 확인하고 `MF-15`로 이동할 수 있습니다.
3. 소상공인 `SB-12`에서 5개 필수 조건 확인 전 시작은 비활성입니다. 모두 확인 후 `SB-13`에서 구간 버튼을 눌러 기록하고 제출합니다.
4. 검수 역할로 바꾸어 `SB-15`의 ‘내 데모 세션 검수’에서 승인합니다. 원본 샘플의 품질 미충족 승인 버튼은 그대로 비활성입니다.
5. `SB-19`에서 검수 승인만으로 내보내기는 불가합니다. 평가 목적 이용 신청 → 운영팀 역할로 모의 승인 후 데모 JSON을 내보낼 수 있습니다. 지급 상태는 계속 모의 지급 대기입니다.

## 검증 결과와 한계

- 빌드: 제조업 21개·소상공인 20개, 누락·중복 충돌 없음.
- 자동 검사: 원본 SHA-256 일치, 41개 페이지·내부 링크·로컬 CSS, 원본 실행 스크립트·인라인 핸들러 제거, 조건·직무·검수·이용 상태 분리, 모든 화면 HTTP 200 및 소스 경로 미노출.
- 브라우저: 두 앱 소개, 제조업 개요·등록·상세·FDE 실행 제한/허용, 소상공인 지도·목록 및 수집→검수→이용 승인 흐름 확인. 해당 검증 중 앱 콘솔 오류 없음.
- 모바일 전용 화면의 좁은 컨테이너와 클릭 흐름을 확인했습니다. 테스트 브라우저에서 뷰포트 크기 변경이 적용되지 않아 실제 320/375/768px 반응형 검증은 미완료입니다. 실기기·전체 접근성 적합성 검증도 별도입니다.
- Google Fonts·Material Symbols·Stitch의 Google 이미지 URL에는 네트워크가 필요합니다. 이미지 원격 보존·오프라인 패키지는 보장하지 않습니다. Play CDN 실행은 제거하고 Tailwind CSS는 빌드에 포함했습니다.
- 원본 `SB-01/screen.png`의 손상은 경고로 남기고 정상 HTML을 사용했습니다. 원본은 보존했습니다.
- 원본에 있는 센서·RFM·자동 비식별화·인증·고용·보상 수치·법적 표현은 검증된 요구사항이 아닙니다. 일부 오해 소지가 큰 문구를 빌드에서 완화하고 공통 안내를 추가했습니다. 공개 출시 전에는 기획서와의 전체 문구 대조·권리 검토가 필요합니다.
- 역할 전환과 localStorage는 시연을 위한 것이며 실제 사용자 인증·서버 권한·영속 DB가 아닙니다. 백엔드 구축 시 반드시 서버에서 재검증해야 합니다.
