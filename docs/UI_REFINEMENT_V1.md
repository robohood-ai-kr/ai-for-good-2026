# RoboHood UI 개선 · image-to-code v1

## 결과와 유지한 경계

제조업 21개, 소상공인 20개 화면 이미지를 새로 생성하고 실제 HTML/CSS로 구현했다. 두 제품의 기능·메뉴·브라우저 저장소는 분리했으며 **각각 v1**이다. 기존 생성 이미지와 Stitch 원본을 보존했다.

후속 이미지 대비 보완에서는 41개 화면의 실제 렌더링을 반복 비교하여 화면별 배치·사진·일러스트·여백·모바일 입력을 조정했다. 결과와 의도적으로 남긴 차이는 [시각 보완 기록](UI_VISUAL_CONVERGENCE_V1.md)에 정리했다. 이후 사용자 요청으로 메뉴 오류 수정본까지 [Vercel에 재배포](VERCEL_DEPLOYMENT_V1.md)했으며 최종 빌드·자동 테스트는 **75/75 통과**했다.

이번 결과는 프런트엔드 데모다. 실제 계정·서버 업로드·AI 판정·모델 학습·로봇 제어·지도 서비스·계약·고용·지급은 연결하지 않았다. 생성 화면의 예시 수치를 사업 성과로 해석하지 않는다.

## 장점을 어떻게 합쳤는가

| 기준 | 채택한 장점 | 구현 |
|---|---|---|
| 이전 이미지 | 쉬운 설명, 한 과제를 따라가는 흐름, 청년·현장 중심 | 대시보드 6단계 흐름, 다음 행동, 참여자·작업 사진 카드 |
| Stitch | 파란색 업무용 UI, 명확한 탐색, 상세 기록 | 공통 사이드바, 과제 표, 검수 3분할, 데이터셋·이용 승인 화면 |
| DESIGN.md | 한글 가독성, 색상 역할, 간격, 반응형 | 파랑 `#2563EB`, 청회색 `#F4F7FB`, 흰 카드, 본문 17px, 모바일 재배치 |
| 기획의 역할 경계 | 수집·검수·FDE 구분, 승인·지급 구분 | 별도 역할 선택, 검수 및 운영팀 제한, 상태별 카드·안내 |

원본을 겹쳐 보여 주던 도구 모음·진행 패널을 제거하고 하나의 앱 셸로 통일했다. 수치는 정적 KPI 대신 현재 브라우저의 과제·검수·승인 기록에서 표시한다. MUI·KRDS를 실제 설치하거나 공식 적합성 인증을 받은 것은 아니다.

## 실행

```sh
npm ci
npm run dev
# 빌드만: npm run build
# 빌드 + 자동 검사: npm run check
# 기존 빌드 서버: npm run preview
```

| 화면 | 로컬 주소 |
|---|---|
| 앱 선택 | `http://127.0.0.1:4173/` |
| 제조업 대시보드 | `http://127.0.0.1:4173/manufacturing/mf-03.html` |
| 제조업 새 이미지 21개 | `http://127.0.0.1:4173/manufacturing/image-gallery.html` |
| 소상공인 대시보드 | `http://127.0.0.1:4173/small-business/sb-03.html` |
| 소상공인 새 이미지 20개 | `http://127.0.0.1:4173/small-business/image-gallery.html` |

`npm run build:manufacturing` 또는 `npm run build:small-business`는 해당 제품만 다시 빌드한다. 선택 허브의 두 제품을 모두 열려면 처음에는 전체 빌드를 실행한다. HTML 더블 클릭 대신 HTTP 서버로 확인한다. 외부 네트워크 자산 없이 로컬 CSS·SVG 아이콘·PNG를 사용한다.

`npm run package`는 빌드·검사 후 `dist/packages/robohood-manufacturing-v1-refined.zip`, `robohood-small-business-v1-refined.zip`을 만든다. 활성 화면·자산만 포함하며 이전 이름의 Stitch 빌드 ZIP은 덮어쓰지 않는다.

한 PNG에 하나의 화면 ID가 대응한다. 실행 화면 하단의 ‘이 화면의 생성 시안’으로 원본을 확인할 수 있다. 이미지 전체를 배경에 붙이거나 픽셀 좌표에 클릭 영역을 얹은 것이 아니다. 생성된 사진·장식 일러스트 외에는 텍스트·폼·버튼·상태를 HTML로 구현했다.

## 동작하는 데모

- 제품별 과제 등록·임시 저장·검색·역할 전환·진행 기록. 새 과제를 등록할 때 기존 과제 메타데이터를 이력에 보존한다.
- 다섯 가지 조건을 모두 확인해야 수집 시작: 교육·과제 적격, 현장 촬영 허용, 안전·감독, 수행 범위·시간, 보상·보완 조건.
- 제조업: 생성 부품 사진을 이용한 RGB 샘플·라벨 초안 기록, 검수, 별도 FDE 역할의 브라우저 UI 모의 실행·중단·재수집 요청 초안.
- 소상공인: 로컬 영상 미리보기, 시작·끝 시간과 이름·성공 여부·환경 메모의 구간 기록, 검수 제출. 빈 값·역전된 시간·영상 길이 초과를 거부한다.
- 검수 담당은 4개 검수 항목 확인 후 승인하며 보완 요청에는 사유가 필요하다. 검수·이용 승인·지급 상태를 서로 섞지 않는다.
- 이용 목적 신청 후 운영팀 모의 승인. 승인된 경우에만 데모 JSON 메타데이터를 내보낸다. 원본 영상·이미지 다운로드나 학습·공유 허가가 아니다.
- 준비·수집·보완 시간의 표시와 모의 지급 대기 상태. 실제 지급 처리 기능은 없다.

저장소 키는 `robohood:manufacturing:v1`, `robohood:small-business:v1`이다. URL에 `?qa=1`을 붙인 테스트는 별도 `:qa` 키를 사용해 일반 데모 기록과 분리한다. 역할 선택은 브라우저 시연일 뿐 서버 보안 경계가 아니다.

로컬 영상은 256MB 이하 파일을 브라우저에서만 임시 미리보기 한다. 서버에 전송하지 않고 파일 내용을 localStorage에 보존하지도 않는다. 수집 페이지를 떠나면 미리보기 URL을 해제하므로 검수 화면에서는 영상 자체가 아닌 기록된 구간 메타데이터만 확인한다.

## 최초 image-to-code 시점의 검증과 남은 제약

아래 58개 검사와 ZIP은 최초 구현 당시 기록이다. 후속 시각 보완의 74개 검사 및 164회 반응형 점검은 [최신 검증 기록](UI_VISUAL_CONVERGENCE_V1.md#검증-결과)을 따른다. ZIP은 이번 시각 보완 후 다시 패키징하지 않았다.

- 최종 `npm run package`: 두 앱 빌드 및 자동 검사 **58/58 통과**, 별도 ZIP 두 개 생성.
- 자동 검사: 기존 원본 해시, 41개 화면·로컬 링크·CSP, 상태 전이, 구간 유효성, 과제 이력 보존, 새 PNG와 빌드 SHA-256 대응을 검사한다.
- 브라우저: 전체 41개 화면을 320·375·768·1024·1440px 너비에서 열어 이미지 로드·가로 넘침을 확인했다. 해당 점검에서 가로 넘침·깨진 이미지·콘솔 경고/오류는 발견하지 않았다. 375·1440px에서는 모든 화면의 주 제목도 확인했다.
- 직접 확인한 흐름: 소상공인 조건 4/5에서 시작 차단, 5/5에서 시작, 잘못된 구간 거부, 정상 구간 추가·제출, 검수 기준 미확인 승인 거부, 검수 승인, 운영팀 외 이용 승인 거부, 이용 승인 후에도 지급 대기 유지. 제조업은 일반 역할의 모의 실행 거부 및 FDE 역할 허용을 확인했다.
- 로컬 영상 선택·재생과 파일 다운로드의 실브라우저 검증, 실기기, 스크린리더 및 전반적인 접근성 적합성, 서버 연계는 별도 검증이 필요하다. 전체 기능의 완성이나 모든 경로의 E2E 통과를 뜻하지 않는다.
- 지도는 가상 SVG 배치이며 실재 위치·사업장·거리 검색이 아니다. 사진은 생성 이미지이고 과제는 대표 예시 하나를 사용한다.
- 이미지 속 세부 글자·표시 수치는 시안이다. 코드에서는 기획서의 용어·책임 경계와 현재 데모 상태를 우선하며 완전한 픽셀 복제를 주장하지 않는다.

최초 구현 당시에는 Git 커밋·푸시·공개 배포를 수행하지 않았다. 이후 사용자 요청으로 변경사항을 `main`에 커밋·푸시하고 production에 재배포했다. 현재 상태는 [배포 기록](VERCEL_DEPLOYMENT_V1.md), 이전 Stitch 병합 시점의 기록은 [STITCH_BUILD_V1.md](STITCH_BUILD_V1.md)에 보존한다.
