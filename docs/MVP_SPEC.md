# RoboHood 제조업 중심 MVP 구현 명세 v1

- 기준일: 2026-09-18 (최초 v1: 2026-09-17)
- 기준: [제품 기획서 v1](AI_FOR_GOOD_PROJECT_PLAN.md)
- 상태: 개발 요구사항. 아래 항목의 구현·시험 완료를 뜻하지 않는다.
- 우선순위: 제품 목적은 기획서, 기능과 수용 기준은 이 문서, 현장 운영은 [운영 원칙](OPERATIONS.md)을 따른다. 생성 이미지의 수치·문구를 구현 명세로 간주하지 않는다.

## 1. 대표 시나리오와 범위

가상의 AI 연구팀이 소형 부품 외관 검사에 필요한 RGB 이미지와 전문가가 정한 라벨 기준을 요청한다. 제조기업의 모의 작업대에서 교육·보상 조건을 확인한 **청년 Physical AI 현장 전문인력**이 촬영·기록·라벨 초안을 수행한다. 검수 담당자가 확정한 버전을 현장 적용 FDE가 모델 평가·장치 반응과 연결하고, 실패 사례를 재수집한다. 청년 현장 전문인력이라는 명칭이 모든 기술 업무의 권한을 뜻하지 않는다.

제조기업이 직접 과제를 요청하는 경우도 같은 과제 구조로 표현한다. 요청자와 현장 제공자가 반드시 다른 조직일 필요는 없다.

| 영역 | MVP에서 구현 | 후속 범위 |
|---|---|---|
| 과제 등록 | 요청 조직·목적, 현장, RGB 수집·검수 조건 | 다양한 산업·데이터 유형별 템플릿 |
| 수행 배정 | 수집팀·직무·담당자 수동 선택, 교육·안전·보안 확인, 업무·예상 시간·보상 조건 | 거리·숙련도 기반 자동 추천, 다지역 운영망 |
| 수집·검수 | 이미지 입력, 라벨·촬영 조건, 승인·반려 기록 | 다중 센서 동기화, 3D·행동 데이터 파이프라인 |
| 데이터셋 | 자체 저장·조회, 버전 구분, 출처·조건 추적 | 대규모 스트리밍·데이터 거래 |
| 모델·장비 | 숙련 기술 담당자의 한 판별 방식·적용 버전·장치 연결, 수집 직무와 권한 분리 | RFM 신규 학습, 제조사별 자동 호환성 보장 |
| 운영·재수집 | 실행 상태·오류 기록, 원인과 재수집 버전 연결 | 무인 로봇군 운영, 자동 재학습·재배포 |

지도는 보조 탐색 기능이며 핵심 흐름보다 우선하지 않는다. [21개 UI 시안](UI_SCREEN_PLAN.md)은 전체 서비스의 화면 제안으로, 모두 MVP 구현 대상이거나 구현된 페이지라는 뜻은 아니다.

## 2. 최소 데이터 정의

아래는 기능 간 연결에 필요한 논리 항목이다. 데이터베이스·클라우드·API 기술 선택을 확정하지 않는다.

| 단위 | 기록할 핵심 항목 |
|---|---|
| 과제 | 식별자, 요청자·조직, 활용 목적, 제공 현장·지역, 수집팀·담당자·직무, 수집·검수 조건, 진행 상태 |
| 배정·업무 이력 | 직무·필수 교육·평가·승인 상태, 감독자, 수행 범위·시간, 보상 조건·비용 부담자, 실제/모의 지급 구분 |
| 수집 세션 | 과제, 수행자, 수집 시점·장비·촬영 조건, 안전·수집 허용 확인 상태 |
| 데이터 항목 | 원본 참조, 정상·불량 또는 판정 보류 라벨, 수집 세션, 검수 결과·사유 |
| 데이터셋 버전 | 포함 항목, 이전 버전, 변경 사유, 품질 기록, 제공자·수집 수행자, 이용 조건·보관기간 |
| 모델 적용 기록 | 모델·버전 또는 규칙 식별자, 목적, 입력 형식, 사용 데이터셋 버전, 평가 조건·결과 |
| 배포·운영 이벤트 | 적용 모델·장치 버전, 실제 장치/시뮬레이터 구분, 입력·판별·동작·오류, 관련 과제·재수집 참조 |

현장 정보는 데모에서는 가상 정보만 사용한다. 실증 시 상세 위치·영상·개인정보의 수집 범위는 사전에 합의한다. 이용 조건에는 조회·평가·학습·재배포의 허용 여부를 구분하며, 수집을 허용받았다는 이유로 모든 용도의 이용을 허용하지 않는다.

첫 데모의 목적은 외관 판별 **평가·적용**이다. 데이터 업로드가 곧바로 모델 학습을 실행하지 않는다. 향후 학습에 사용할 경우 데이터 적합성과 이용 범위를 별도로 확인한다.

## 3. 사용자 동작과 상태

1. 요청자가 과제의 활용 목적과 데이터·검수 조건을 입력한다.
2. 제공 현장의 수집 허용 범위와 안전·보안 조건을 확인한다.
3. 수행팀과 청년 현장 전문인력을 배정하고 교육·감독·보상 조건을 확인한다. 수락·확인 전에는 수집을 시작할 수 없다.
4. 청년 현장 전문인력이 이미지·라벨 초안·수집 조건을 입력하고 검수를 요청한다. 라벨 확정·장비 제어 권한은 별도로 관리한다.
5. 검수 담당자가 승인·반려 및 사유를 남긴다. 승인된 데이터 묶음의 버전을 만든다.
6. 승인된 숙련 기술 담당자가 해당 버전으로 판별 모델을 평가하고 입력·출력 조건이 맞는 장치를 시험한다.
7. 운영 이벤트에 모델·장치·데이터 버전과 실제/모의 실행 여부를 남긴다.
8. 실패 사례를 후속 수집 과제와 연결한다. 검수 후 새 데이터셋 버전을 만들되 이전 기록은 덮어쓰지 않는다.

과제 상태는 요청 → 배정 대기 → 수집 → 검수 → 적용 준비 → 시험 운영으로 표현한다. 반려는 수집 보완으로 돌아가고, 실패는 원래 운영 이력을 유지한 채 별도 재수집 작업으로 연결한다.

## 4. 수용 기준과 검증 증거

| 확인 사항 | 수용 기준 | 남길 증거 |
|---|---|---|
| 요청·수행 역할 | 요청자, 제공 현장, 수행팀·담당자를 각각 저장·조회 | 한 조직이 복수 역할인 사례와 서로 다른 조직인 사례 |
| 직무·유급 업무 조건 | 직무·필수 교육·감독·보상 확인 전 수집 시작 차단, 수집 담당자의 배포 실행 차단 | 미이수·미승인 거부 시험, 작업시간·보상 조건·모의 지급 표시 |
| 실제 데이터 입력 | 카메라 입력 또는 출처를 명시한 재현 가능한 샘플 입력 | 수집 세션, 이미지·라벨·촬영 조건 |
| 독립 데이터 관리 | 외부 데이터 플랫폼 계정·API 없이 자체 저장·조회, 버전 구분 | 데이터셋 목록·상세, 저장·조회 시험 |
| 검수·추적 | 승인·반려 사유와 버전 변경, 모델·장치·재수집 연결 | 한 실패 사례의 관련 기록 조회 |
| 판별 실행 | 입력에 따라 실제 모델 또는 명시된 규칙이 동작 | 사용 방식·버전, 입력과 결과, 평가 조건 |
| 장치 반응 | 실제 장치 제어 또는 명시된 시뮬레이터의 상태 변화 | 명령·응답·실패 로그와 실제/모의 표시 |
| 이용 조건·접근 | 과제별 허용 범위를 표시하고 권한 없는 조회·내보내기를 차단 | 허용·거부 시험, 데이터 이용 조건 |
| 전체 재현 | 대표 시나리오를 처음부터 재수집 버전까지 실행 | 실행 절차와 결과·미충족 항목 기록 |

실제 시험하지 않은 정확도나 성공률은 표시하지 않는다. 규칙 엔진으로 동작하면 AI 모델 검증으로 보고하지 않는다. 역할 선택 UI만으로 권한 통제를 구현했다고 판정하지 않는다.

## 5. 하드웨어·현장이 없을 때

- 실제 공장 접근 전에는 모의 공정이나 촬영 허용된 부품으로 수집을 검증한다.
- 스마트폰·웹캠 이미지 입력과 브라우저·로컬 판별 실행을 최소 대안으로 삼는다.
- LED·서보 등 장치가 없으면 장치 API 시뮬레이터가 명령을 받아 상태·이벤트를 반환하도록 구현한다.
- 화면의 상태 변화만 애니메이션으로 보여주는 것과 실제 코드로 연결된 시뮬레이션을 구분한다.
- 사전 데이터 재생, 규칙 엔진, 장치 시뮬레이터를 썼다면 각각 명시한다. 결과는 ‘배포 흐름 검증’이며 ‘산업현장 배포 완료’가 아니다.
